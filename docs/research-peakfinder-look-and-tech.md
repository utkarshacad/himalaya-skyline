# Redraw Himalaya Skyline as PeakFinder's ink

PeakFinder's look comes from one choice: **it draws terrain as lines, not as shaded colour**. The panorama is a stylised line drawing taken from an elevation model. The skyline is the heaviest stroke, interior ridges are thinner, and ink lightens toward a user-set visibility range of up to **320 km**. On top of that sit compact name-and-height labels, a telescope reticle, and eased camera parameters (azimuth, pitch ±25°, FOV 8–90°, and a raised-eye "elevation offset") that can all be animated ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)). Himalaya Skyline v1 already has most of the hard parts: a Web Worker ray-marcher over AWS Terrarium tiles, a depth buffer, line-of-sight tests, and rivers traced from the terrain itself. What it lacks is the drawing style and the interaction model. v1 fills the land with a blue distance-haze colour and draws a ridge line only where the depth jump exceeds `lastD·1.1 + 250 m`. That rule all but guarantees an empty dark wedge in the first few kilometres, which is exactly what the Pangarchulla screenshot shows. v1 also re-renders on every drag, where it could pan a pre-rendered 360° strip. Five changes would close most of the gap, and none needs new data: flat dark-grey fill, an angular crest test with a near-field z12 level, slanted labels with leader lines, a 360° render-once/pan-free pipeline with inertia, and a visibility slider that sets `maxD`. Terrain plus the existing traced rivers cover the "minimal data" brief. The only bake worth adding soon is a small OSM peak and lake JSON. One caveat applies throughout: peakfinder.com and the app stores could not be reached during research. The PeakFinder facts below therefore rest on the official JS API README and search snippets of store pages and reviews, while the slanted-label and dark-theme specifics come from the owner's reference screenshots.

## PeakFinder is a line drawing with a fade, not a rendered landscape

The API documents the core visual parameters. The default theme is light ("normally the sky is white") and `theme: 'dark'` switches it. Projection is either perspective or cylindrical, an optional coordinate grid can be shown, and sun and moon "ecliptics" can be drawn as arcs across the sky ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)). The owner's screenshots use the dark theme. They show dark grey ground with no colour gradient, fine white ridge lines packed densely all the way into the foreground, and a plain dark sky. Reviewers call the result a **"hand-drawn-style panoramic sketch"** that is "beautifully clear", and one praises the visibility setting because it "realistically 'fades' the mountains out" ([reviewed.app](https://reviewed.app/app/peakfinder/), [The Oikofuge](https://oikofuge.com/peakfinder/), [App Store](https://apps.apple.com/au/app/peakfinder/id357421934)). Distance, then, is carried by line brightness, not fill colour. That is the key aesthetic difference from v1.

PeakFinder's actual line algorithm is unpublished. The best public description of how to imitate it is an open-source reimplementation, alpimaps PR #149, titled "draw peakfinder.com's look". It uses:

- a flat surface with pure ink;
- silhouettes found from an inverse-depth Laplacian;
- a skyline stroke heavier than any "interior fold";
- extra ridge ink taken from **DEM curvature**, so folds and spurs that are not occlusion edges still get lines;
- an optional sun-driven hillshade;
- a distance ink floor, so "the far ranges lighten" ([alpimaps PR #149](https://github.com/Akylas/alpimaps/pull/149)).

That curvature ink is the likely source of the dense foreground lines in the reference screenshots. Pure occlusion edges are sparse close to the viewer, because near slopes are seen continuously and hide nothing.

The engine is fast because it ships very little. PeakFinder renders out to about **300 km** in real time from terrain blended from NASADEM, SRTM and European LiDAR. A later "new data model" needs less data and auto-loads about a **150 km radius** around the user ([Wikipedia via snippet](https://en.wikipedia.org/wiki/PeakFinder), [AppGrooves](https://appgrooves.com/app/peakfinder-ar-by-fabio-soldati), [apk4free release notes](https://apk4free.net/peakfinder-ar/)). The API exposes `hasMultiThreadingSupport()` and `hasSimdSupport()`, which strongly suggests a compiled WebAssembly/WebGL core shared with the native apps. That is an inference: the stack is not stated anywhere ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)). For our purposes the lesson is not "use WASM". It is that the engine moves only a heightfield with no imagery and draws untextured geometry, so panning costs almost nothing.

## Every control in the reference screenshots maps to a documented API knob

The sliders panel opens from a button at bottom left. It holds compass correction, **visibility range** (`visibilityRange()`, 0–320,000 m), date/time for the sun and moon, and a **minimal elevation** for peak names (0–10,000 m), which works as a declutter control ([peakfinder.com/mobile snippet](https://www.peakfinder.com/mobile), [PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)). The calendar, eye and flag icons in the owner's screenshot correspond to date, visibility and elevation/marks. No source says whether visibility only clips or also dims labels. Mechanically, a shorter range removes the farthest ridge layers and their peaks, which is the "how many range layers show" behaviour the owner noticed.

The camera is three animatable parameters: `azimut(val, secs)`, `altitude(val, secs)` (pitch, ±25°) and `fieldofview(val, secs)` (8–90°). The official demo eases to azimuth 209° over 2 s and FOV 45° over 2 s after loading a viewpoint ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)). The **fly-up** feature is `elevationOffset(metres, secs)`, a control on the left edge. The shipped example raises the eye **1,000 m over 5 s** and brings it back down over another 5 s ([elevation-offset example](https://github.com/Fabiz/PeakFinder-API/blob/main/basicexample_canvas_elevationoffset.html)). Changing viewpoint runs a "journey" that **walks, flies or teleports depending on distance** ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API)), and a bird icon lets the user "fly" on a mountain ([peakfinder.com/mobile](https://www.peakfinder.com/mobile/)). No source gives easing curves or pan-inertia constants. Those have to be tuned by eye.

Labels show name and height, with distance as an option since v4.8.73. Tapping a label or centring the **telescope** fires a `poiinfo` event that opens an info sheet. The telescope object reports centre azimuth, altitude, distance and elevation ([PeakFinder-API README](https://github.com/Fabiz/PeakFinder-API), [ipa4fun history](https://www.ipa4fun.com/history/180953/)). That matches the screenshot's info bar, "Mount Rainier 4392 m · 89.8 km, 152.7°". The slant and the thin leader lines are confirmed only by the screenshots. The slant has a practical job: a label rotated about 45–60° takes only about one line-height of horizontal space, so dozens of peaks fit along a crowded Himalayan skyline without overlapping. alpimaps imitates PeakFinder's "row behaviour", in which a band above the skyline is the highest a label may sit ([alpimaps PR #149](https://github.com/Akylas/alpimaps/pull/149)).

**Marks** let users tag favourites, visited peaks, peaks to climb, and Home. Home is there so you can check whether your house is visible from a summit. Marks sync with an account ([peakfinder.com/mobile](https://www.peakfinder.com/mobile/)). They are app-only and not exposed in the API ([alternativeto PeakOrama](https://www.alternativeto.net/software/peakorama/about/)). The heart, star, bookmark and home icons come from the owner's screenshot.

## Gap: v1 vs PeakFinder

Reading the v1 renderer (`render()` in `index.html`, described in `docs/technical-design.md`) explains each visual gap directly.

| Aspect | PeakFinder (dark theme) | Himalaya Skyline v1 | Root cause in v1 |
|---|---|---|---|
| Ground | Flat dark grey; lines carry all depth | Blue NEAR→FAR haze fill, slope light, snow tint | Fill colour interpolates `#0e1622`→`#3b5575` with distance |
| Foreground | Dense fine lines right to the viewer | One flat dark wedge | Ridge drawn only if `d > lastD·1.1 + 250`; the +250 m kills crests in the first ~2–3 km; no curvature/fold ink; level 0 is z11 (~66 m) |
| Layer count | Many ranges, fading toward the visibility limit | Few layers | Same distance-jump rule merges nearby ranges; line alpha floor 0.4 gives little gradation |
| Labels | Slanted white "Name 3903 m" + leader line, declutter by min elevation | `?` quiz markers only | Quiz-first design; no learn/reveal label style |
| Panning | Smooth, low lag | Half-res re-render every ~70 ms while dragging, then 475 ms full render | Each view is ray-marched from scratch, even though the projection is cylindrical |
| Visibility range | Slider 0–320 km | Fixed `maxD` = 235 km | No UI |
| Fly-up / journeys | Animated eye-height offset; walk/fly/teleport | MapLibre `flyTo` into the viewpoint only | Eye height is fixed after snapping |
| Telescope | Centre reticle with name · elevation · distance · bearing bar | None | — |
| Chrome | Round dark corner buttons, compass top right, sliders panel, marks bar | Permanent circular mini-map top left, degree ruler at bottom | The mini-map conflicts with the project rule "never add a panel that permanently covers the map" |
| Water | Not a PeakFinder feature | Rivers traced and glinting (an advantage) | — |

The biggest single lever is the ridge rule. Front-to-back marching already knows the *angular* profile of each column. A crest is a sample after which the terrain's elevation angle falls by some threshold before it rises again. The 2026 browser clone uses "ground behind drops ≥ 0.05° below it" and links crests between neighbouring rays when they agree within 8 % + 150 m in distance and 0.6° in angle ([nightskyfinder PLAN.md](https://github.com/nightskyfinder-app/peakfinder/blob/main/PLAN.md)). An angular test scales naturally with distance, so it catches a 30 m spur 800 m away as readily as a range 80 km away. A distance-ratio test (`Δd/d > τ`) does the same in depth space and avoids the classic false-edge problem at the horizon ([Godot depth edge notes](https://godotshaders.com/shader/depth-based-edge-detection-with-sobel-operator-screenspace/)).

## A 360° render-once pipeline makes panning free

v1 already uses a cylindrical projection, where column means azimuth. **A pure azimuth pan is therefore a horizontal translation of an image that has already been rendered**, and needs no new ray-march. The fix is architectural. When a viewpoint loads, have the worker march all 360° once at the highest pixels-per-radian you intend to show. At the current 1400 px / ~60° FOV that is roughly 8,400 columns. Measured cost is about 475 ms per 1,400 columns, so the full ring takes about 3 s on one worker and under 1 s split across four. Render the visible sector first so the user is never left waiting.

The result should be cached as **vectors, not pixels**: crest polylines with distance, plus per-column skyline height and a coarse depth profile. Each frame then strokes those lines on a Canvas2D or WebGL layer at the current offset, pitch and zoom. Lines stay crisp at any FOV, and drawing a few thousand polylines takes well under a frame. This is the hybrid the renderer research recommends: compute crests once per observer in a Worker, then treat pan and zoom as pure transforms, and recompute only when position or eye height changes ([renderer notes; nightskyfinder PLAN.md](https://github.com/nightskyfinder-app/peakfinder/blob/main/PLAN.md)). Pitch is a vertical shift. FOV zoom beyond the baked resolution can trigger a quiet refinement of the visible sector only.

Inertia is a few lines of code. Keep the angular velocity ω at release, decay it with `ω *= exp(−dt/τ)` where τ ≈ 0.4 s, and drive every camera parameter through frame-rate-independent damping, `x += (target − x)(1 − e^(−k·dt))`. This is engineering practice, not a documented PeakFinder constant.

The **fly-up** follows the same logic. Tween eye height with ease-in-out over about 5 s, matching PeakFinder's example. Have the worker render cheap low-resolution 360° keyframes at a few heights (+0, +250, +500, +1,000 m), crossfade between them during the tween, and run one full-quality render when it lands. A shorter `maxD` during the climb keeps those keyframes cheap. Viewpoint changes can copy PeakFinder's walk/fly/teleport split: MapLibre's `flyTo` (already used for fly-in) for flights, and a crossfade for teleports.

## Terrain and water are enough; add only small baked JSON

The current data path is the right minimum. Terrarium decodes as `R·256 + G + B/256 − 32768`, is CORS-open, and uses SRTM outside the US ([tilezen/joerd formats](https://github.com/tilezen/joerd/blob/master/docs/formats.md)). Two upgrades are cheap.

First, add a **z12 level within about 5 km**. At 31°N a 256 px z12 tile is about 33 m per pixel, against 66 m at z11. That resolution is what produces fine foreground ridges, and the source data runs out at about this zoom anyway ([data notes; FME docs](https://docs.safe.com/fme/2017.1/html/FME_Desktop_Documentation/FME_ReadersWriters/terraintilesaws/terraintilesaws.htm)). Only a handful of extra tiles are needed.

Second, evaluate **Mapterhorn** as a drop-in replacement. It uses the same Terrarium encoding, as 512 px WebP in PMTiles, built from **Copernicus GLO-30** up to z12 ([Protomaps blog](https://protomaps.com/blog/mapterhorn-terrain/), [terrain-viewer docs](https://terrain-viewer.iconem.com/docs/features/terrain-sources/)). GLO-30 is TanDEM-X based with documented void filling ([ESA](https://earth.esa.int/eogateway/documents/20142/2982981/3_Leister_2.pdf/1f084495-7cf3-7b88-d4d6-cb363dadbfa0)), and SRTM has voids on steep shadowed slopes. It probably sharpens Himalayan summits, but nobody has benchmarked it for this region, and its CORS headers must be tested from the browser first. If live fetching proves fragile, a self-hosted **z5–z9 PMTiles pyramid at about 250 m resolution is roughly 65–105 MB** for the whole bbox, as an estimate. That fits static hosting, with near-field tiles still streamed live ([data notes](https://protomaps.com/blog/mapterhorn-terrain/)).

For water, v1's own priority-flood plus flow accumulation (10,739 segments in about 445 ms on Kausani) already beats any downloaded river network for placement, because the lines sit exactly in the rendered valleys. Names are the missing piece. A one-off Overpass extract of named `waterway=river` and `natural=water` for the Himalayan bbox, simplified with mapshaper, should come to well under 1 MB gzipped. HydroRIVERS adds stream order for ranking but carries no names; OSM is ODbL and HydroRIVERS requires attribution ([HydroRIVERS](https://hydrosheds.org/page/hydrorivers), [OSM wiki](https://wiki.openstreetmap.org/wiki/Tag%3Anatural%3Dpeak)). Lakes are worth drawing as a flat glint in the mid-field. RGI 7.0 regions 14 and 15 cover glaciers later if needed ([RGI regions](https://www.glims.org/rgi_user_guide/02_regions_definition.html)).

Peaks should move from hand-snapped coordinates to a baked **OSM `natural=peak` JSON** joined to **Kirmse prominence**. That costs about 50–100 bytes per peak, so roughly 1–2 MB for 20,000 peaks before gzip (estimate). Labels then follow a distance-dependent prominence threshold and the depth-buffer line-of-sight test v1 already has ([akirmse/mountains](https://github.com/akirmse/mountains), [OSM ele quality discussion](https://community.openstreetmap.org/t/highest-peaks-in-openstreetmap/108578)). Reject heights above 8,900 m and flag heights that look like feet, because OSM `ele` values in the region are noisy.

## Conclusion

Closing the gap is mostly subtraction and caching, not more data. v1 tries to look like a painted landscape. It spends its effort on colour gradients and pays a full ray-march on every drag, when the PeakFinder look comes from deliberately throwing colour away and letting a dense, distance-faded line hierarchy carry depth. Because v1's cylindrical projection already turns panning into translation, a render-once vector cache delivers PeakFinder-class smoothness inside the existing single-file, Worker-based design. No WebGL terrain engine or WASM port is needed.

The opportunity unique to Himalaya Skyline is that PeakFinder does not draw water. Once the ink style is right, glinting traced rivers become the one colour accent on a monochrome panorama, which makes them both a striking visual signature and a natural "handrail" for the planned game modes. Several things remain unverified and should be checked in a browser against peakfinder.com: label angle and spacing, the visibility fade curve, whether out-of-range labels hide or dim, and the inertia constants.
